2 概述

2.1 产品描述
本产品是一个多角色、多端协同的综合性在线旅游预订平台。它不仅为前端的游客与顾客提供了便捷的旅游产品浏览与预订服务，还为后端的商家提供了一套高效的店铺与订单管理系统，同时，平台维护人员可以通过统一的管理后台对整个平台的业务进行监控与配置。

2.2 主要功能（业务流程图）
要实现的业务管理功能如下：
1.	客户信息管理
1.1 负责客户的注册、登录与个人信息维护。
1.2	负责接收和处理客户的反馈与举报内容。
2.	商家信息管理
2.1 负责处理商家的入驻申请、资质审核，并维护商家基本信息。
3.	订单管理
3.1 负责处理客户的预订请求，生成和管理订单。
3.2 负责订单状态的流转、异常订单的上报与处理。
4.	商品管理
4.1 负责商家对商品信息的录入、发布与管理。
4.2 向游客和客户提供商品信息的浏览与搜索服务。
2.3 实现语言
本系统将采用 MySQL数据库管理系统作为系统的后台数据库，web服务器采用Apache。前端采用 vue作为编程语言，前端和后端 之间采用RESTful API专用接口进行联接，服务器与客户机之间采用TCP/IP协议 (HTTP/S)进行联接。

2.4 用户特点
2.4.1 现行系统特点
    a. 现行系统概况
目前市场不存在统一的、针对本项目的“现行系统”。用户的旅游预订行为分散在多个独立的OTA平台、社交媒体或线下旅行社中。

b. 管理主要业务
用户需手动在不同平台间进行比价、行程规划；商家则依赖于各大平台的后台或传统方式管理订单和库存。

c. 现行系统的特点
信息孤岛化、操作流程不统一、用户体验参差不齐。

d. 存在的主要问题
预订效率低、信息过载与筛选困难、缺乏个性化推荐、商家管理成本高。

2.4.2系统的目标
•	为游客和客户提供一个信息聚合、流程顺畅、体验优秀的一站式旅游预订入口。
•	为商家提供一个易于操作、功能强大的商品与订单管理后台。
•	为管理员提供一个高效、全面的平台监控与运营管理工具。

2.4.3 用户业务素质
•	游客/客户: 具备基本的互联网浏览和在线购物操作能力。
•	商家: 具备基本的计算机操作能力，能够使用Web后台系统进行信息录入和订单处理。
•	管理员: 具备较高的计算机操作水平和平台业务理解能力。

2.5 一般约束
•	a. 应用范围: 本软件主要针对在线旅游预订业务，构建一个完整的B2C电子商务平台。系统将采用前后端分离的Browser/Server模式。
•	b. 系统结构: 本系统为典型的三层网络应用结构。服务器上运行 MySQL 数据库、Spring Boot后端应用及Nginx Web服务器。各客户端通过互联网访问服务器。
•	c. 并行操作: 本系统基于Web，天然支持多用户并行操作。数据库层面将采用事务与锁机制保证数据一致性。
•	d. 信息交换协议: 系统的服务器上采用 Linux 操作系统，而客户端则覆盖Windows、macOS、iOS、Android等，其信息交换协议由 TCP/IP 内部所提供的交换功能来完成。
•	e. 安全保密的考虑: 系统将对所有用户设置用户口令，并基于RBAC模型，为不同角色设置严格的操作权限，从而保证系统的安全性与保密性要求。
3. 具体需求
3.1 功能需求（DFD DD)
3.1.1 商家管理
负责商家的入驻申请、资质审核、信息维护及日常运营支持。
（1）入驻申请处理
（2）资质审核管理
（3）商家运营支持
 
3.1.2 商品管理
负责旅游产品的信息管理、发布和展示。
（1）	商品信息维护
（2）商品展示服务
 
3.1.3 订单管理
负责订单的生成、状态跟踪和异常处理。
（1）	订单生成与处理
（2）	订单状态管理
 
3.1.4 客户管理
负责客户账户管理、反馈处理和用户服务。
（1）	用户账户管理
（2）	客户服务支持
 
3.2 外部接口需求
3.2.1 用户界面(原型)
•	a. 屏幕格式:
o	. 菜单：整体采用顶部导航栏与侧边栏相结合的布局，符合现代Web应用的操作习惯。
o	. 输入：系统的全部数据输入均采用标准Web表单控件，提供清晰的标签和输入提示，并进行前端实时校验。
o	. 输出：系统的查询结果主要以列表、卡片和详情页的形式在屏幕上进行输出。
•	b. 报表打印格式： 商家后台的财务对账等模块，将提供导出为Excel或PDF的功能，格式将以简洁、清晰的表格为主。
3.2.2 硬件接口
    本系统为纯软件系统，不直接与特定硬件交互。系统运行的硬件环境为通用服务器和个人计算机/移动设备，通过标准网络设备连接。

3.2.3 软件接口
支付接口： 后端需集成微信支付和支付宝的官方SDK，调用其API完成支付流程。
短信服务接口： 后端需调用第三方短信服务的API，用于发送手机验证码。
地图服务接口： 前端需调用地图服务商的JS API，用于展示酒店地理位置 

3.2.4 通讯接口
     本系统前后端通讯采用基于HTTP/S的TCP/IP网络协议。 

3.3 性能需求
a. 输入： 关键信息提供“常用旅客”选择功能，减少重复输入。

b. 处理： 核心交易流程要求在2秒内完成响应。商品搜索响应时间在1秒内。

c. 输出： 列表页面支持分页加载，避免一次性加载过多数据导致页面卡顿
3.4 设计约束
3.4.1 需求遵循的其它标准
•	a. 报表格式： 参照主流OTA平台的订单和报表格式，由UI设计师进行设计。
•	b. 数据命名： 数据库表和字段命名遵循统一的、有意义的英文命名规范。

3.4.2 硬件的限制
系统开发完成后，可运行于任何安装了现代浏览器（Chrome, Firefox, Safari, Edge）的PC或移动设备上。
3.5 属性需求
3.5.1 可使用性
     要求具有较强的容错处理能力，以保证软件的可使用性。在用户误操作的情况下，系统应给出明确、友好的提示信息。

3.5.2 安全性
•	用户密码必须经过哈希加盐后存储，防止明文泄露。
•	所有API接口需进行严格的认证与授权校验，防止未授权访问。
•	有效防范OWASP Top 10中常见的Web安全漏洞，如SQL注入、XSS等。
3.5.3 可维护性
为了保证系统的可维护性，要求具有详细的系统设计文档资料，提供全部的系统源程序，并采用模块化的代码结构，降低耦合度。
3.5.4 可移植性
本系统后台基于Java开发，可移植到任何支持JVM的操作系统。前端基于Web标准，可在所有现代浏览器上运行。
